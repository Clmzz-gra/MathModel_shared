## 一、模型表现

### 子问题 1：Y 染色体浓度与孕周/BMI 关系建模

**最终方案**：双模型分层策略（模型 A：个体内固定效应 + 个体间随机截距；模型 B：中介分析）

| 指标 | 模型 A（估计） | 模型 B（解释） |
|------|:---:|:---:|
| R² / CV R² | 0.248 (CV) | 0.456 (全样本) |
| 核心发现 | 孕周 +5.7%/周，BMI −2.9%/单位 | 中介比例 21.3%，BMI 效应独立于胎儿 DNA 通路 |

**符合预期的**：
- 个体内去均值（demeaning）设计成功隔离了孕周的真实纵向效应与个体间混杂
- 中介分析的 Bootstrap 置信区间估计给出了可靠的间接效应显著性检验
- 月份批次效应被成功识别和控制（2023 下半年数据系统性偏低）
- HC3 稳健标准误验证：所有变量仍高度显著（|t| > 2.6），异方差影响极小

**不符合预期的**：
- CV R² = 0.248，75.2% 的个体内 Y 浓度变异无法解释——这是模型能力的天花板
- WLS 加权方案全部失败（CV R² 从 0.248 跌至 0.023），异方差无法用简单加权消除
- 45% 孕妇的 Y 浓度不呈单调增长——固定斜率是对两类纵向行为的平均
- 高次项和随机森林的增量贡献几乎为零（ΔCV R² < 0.002），线性形式确认为最优但也是上限

**设计决策的成功与失败**：
- ✅ 双模型分层（A 做诚实估计，B 做机制解释）是合理的设计——单一模型无法同时满足两个目标
- ✅ 个体内 demeaning 而非原始值回归，避免了 Simpson 悖论
- ❌ WLS 方案应更早放弃——三种方案全部失败后应果断接受 OLS + HC3

### 子问题 2：BMI 分组与最佳 NIPT 时点

**最终方案**：直接计数 + Wilson 二项比例置信区间 + 两阶段策略（对 40+ 组）

| BMI 分组 | 推荐时点 | 首检达标率 | Wilson 95% CI | 策略 |
|----------|:---:|:---:|------|------|
| [20, 28) | 13 周 | 67% | [21%, 94%] | 单次检测 |
| [28, 32) | 11 周 | 94% | [74%, 99%] | 单次检测 |
| [32, 36) | **12 周** | 89% | [71%, 92%] | 单次检测 |
| [36, 40) | 14 周 | 75% | [30%, 95%] | 单次检测 |
| 40+ | 14 预检 → 18–20 复检 | — | — | 两阶段 |

注：[32, 36) 组在批判审查中从 11 周调整为 12 周（Wilson CI 下界 49% → 71%）。

**符合预期的**：
- BMI 分组策略简洁直观，与临床直觉一致
- p₀ = 0.5 的灵敏度分析显示 88% 人群（[28, 36) 两组）在 p₀ ∈ [0.4, 0.8] 范围内时点完全不变——结论极度稳健
- 两阶段策略（14 周预检 + 18–20 周复检）经量化验证覆盖了 40+ 组所有有数据的 7 人
- Wilson CI 揭示了 [32, 36) 组 11 周的脆弱性，直接导向时点调整

**不符合预期的**：
- Logistic 回归替代方案失败：低 BMI 组系数为负（McFadden R² ≈ 0.001），无生物学意义
- 高 BMI 组（[20, 28)、[36, 40)、40+）样本稀疏，逐格直接计数在尾部极不稳定
- 40+ 组两阶段策略的复检窗口（18–20 周）确实仅以 1 人（A099）为关键参照

**设计决策的成功与失败**：
- ✅ 直接计数法是此项任务最诚实的方法——不做模型假设，不掩盖数据稀疏
- ✅ Wilson CI 增强是批判审查带来的最有价值的改进
- ✅ "测太早可重来，测太晚不可重来"的代价不对称框架驱动了所有策略选择
- ⚠️ p₀ = 0.5 的"补测代价 ≈ 0"前提需要精确化措辞（已在报告修正中处理）

### 子问题 3：多因素验证

**最终方案**：多因素线性回归（排除辅助生育后 n = 256）

| 变量 | 单变量 R² | 精简全模型 p 值 | 增量 R² |
|------|:---:|:---:|:---:|
| BMI | 0.027 | **0.010** | — |
| 年龄 | 0.001 | 0.710 | 0.0006 |
| 怀孕次数 | 0.001 | 0.788 | 0.0001 |
| 生产次数 | 0.000 | 0.846 | 0.0001 |

全模型 R² = 0.028（排除辅助生育）；原报告 R² = 0.109 中约 0.014 来自 4 例辅助生育离群值。

**符合预期的**：
- BMI 是唯一有统计显著性的因素——与问题 2 的分组策略一致
- 排除辅助生育后结论更干净——非 BMI 变量的 p 值从 0.07–0.39 变为 0.63–0.99

**不符合预期的**：
- 原报告将 IVF/怀孕次数（p = 0.074/0.075）断然判为"无贡献"，实际是因 4 例辅助生育离群值产生的虚报信号
- 全模型 R² 仅 0.028——首次达标时间几乎无法用任何测量变量预测
- 残差标准差 2.5–4.8 周意味着相同 BMI 的孕妇首次达标时间可能相差 10–20 周

**设计决策的成功与失败**：
- ✅ 排除辅助生育是正确的保守决策（样本量不足 + 临床管理路径特殊）
- ❌ 原报告未发现辅助生育变量编码问题——将 0/1/2 作为连续变量纳入回归
- ⚠️ "残差太大所以加变量没用"的论证逻辑有循环论证嫌疑（已在报告修正中处理）

### 子问题 4：女胎异常判定

**最终方案**：Fisher LDA（Tikhonov 正则化）+ GC 跨染色体差异 + 测序质控特征

| 指标 | 值 | 说明 |
|------|:---:|------|
| AUC | 0.798 | 中等判别力 |
| 高灵敏召回率 | 93.8% | 16 例异常检出 15 例 |
| 高灵敏特异度 | 26.7% | 假阳性率 73.3% |
| 最强特征 | GC_18-13 (d=0.92), X_conc (d=0.95) | Z 值 |d| < 0.23 |

**符合预期的**：
- GC 跨染色体差异（如 ΔGC_18,13）是具有真实判别力的信号，AUC = 0.783（单变量）
- Fisher LDA + Tikhonov 正则化是唯一能在 90%+ 召回下保持有意义特异度的方法
- 简单替代方案（单特征、OR 规则、等权组合）在高灵敏度约束下特异度全部塌缩为 0%
- Z 值与 GC 差异几乎零相关（r = 0.078）——GC 信号捕捉的是独立于 reads 丰度的片段特征维度

**不符合预期的**：
- 确认书方案（马氏距离 + Z 值评分）的 AUC 仅 0.506，方案前提坍缩
- Z > 3 经典规则的召回率仅 4.48%——远低于临床文献的 > 97%
- Z 值在正常/异常间「几乎完全不可分」（|d| < 0.23, KS p = 0.865）
- 确认书列出的风险预案（MCD 稳健协方差、Box-Cox 变换、秩变换）均未实施——方案被静默替换
- T21 仅 4 例阳性，Fisher LDA 对该染色体的协方差估计本质上不可靠

**设计决策的成功与失败**：
- ✅ 从马氏距离转向 Fisher LDA 是数据驱动下的正确转向
- ✅ GC 含量被证明是有效的判别特征——但这完全是在探索中发现的，非事前假设
- ❌ 方案变更过程缺乏透明度——确认书的预案未被尝试，新方案未在确认书中记录
- ❌ 提交代码仍为马氏距离实现，与报告描述的 Fisher LDA 不一致（需替换）
- ⚠️ 77% 假阳性率在筛查工具定位下可接受，但其临床成本（羊穿风险）需诚实标注

## 三、知识空白

以下领域在建模过程中暴露出知识储备不足：

1. **NIPT 临床工作流与领域知识**：GC bias 的来源和校正策略、Z 值的临床计算方法、NIPT 对不同非整倍体的差异化灵敏度（T21 vs T18/T13）、限制性胎盘嵌合体（CPM）对 NIPT-核型分析一致性的影响——这些领域知识在建模初期严重不足，导致对 Z 值失效的原因分析不够深入。

2. **极小样本下的分类器构建**：n = 16 阳性（T21 仅 4 例）场景下，Fisher LDA 的正则化方案选择、协方差估计的理论保证、泛化误差的诚实估计——知识库中缺乏针对"特征维度 > 阳性样本数"场景的系统指导。

3. **观察性数据的因果推断边界**：回顾性临床数据中 indication bias 的识别、因果语言与关联语言的区分标准、中介分析的因果识别假设（sequential ignorability）的检验——这些方法学边界在报告中被多次触及但未充分展开。

4. **卫生经济学与筛查策略评估**：非对称代价（假阴性 vs 假阳性）的定量框架、质量调整生命年（QALY）计算、筛查策略的成本效果分析——批判审查中审稿人反复要求量化但超出了竞赛建模范围。

5. **GC 含量作为非整倍体生物标志物的文献基础**：GC 跨染色体差异的判别力是经验发现（AUC = 0.783），但缺乏直接支撑的文献——Mouliere et al. (2011) 研究的是片段长度分布而非染色体特异性 GC 含量。

### 版本管理体系（进化方案）

> 对应 D 类问题（5.5, 5.16, 5.18），并为 A 类（方案变更追溯）、E 类（批判级联）提供基础设施。

#### 核心原则：git 是唯一真相源

**不额外维护任何日志文件**。operation-log、build-log、方案变更标记全数取消。git 的 commit 是操作本身——动作与记录是同一个东西，不存在"忘记写日志"的问题。AI 在任何时刻通过 `git log --graph --all` 即可重建全局演进图：谁、什么时候、做了什么、为什么、影响了哪些文件。

关键能力：**diff 不可说谎**。operation-log 声称"修了时点 11→12 周"只是一句声明，git diff 精确显示了改了什么行、有没有顺便改别的东西。

#### 1. 分支策略 — 所有非平凡操作都在分支上

不再是"审查时用分支"，而是**默认在分支上工作**：

| 场景 | 分支命名 | 从哪切 | 合并条件 |
|------|------|------|------|
| 子问题方案探索 | `experiment/sub{N}-{方案}` | 上一个稳定提交 | 方案确认后人类合并 |
| 方案回溯 | `backtrack/{触发阶段}-to-{目标}` | 触发点的父 commit | 下游验证通过后人类合并 |
| 批判审查 | `review/round-N` | 阶段 3.0 前的主线 | 人类确认修正清单后合并 |
| 数据修正 | `fix/data-{问题简述}` | 发现问题的 commit | 重新清洗→重新建模验证后合并 |

分支即决策分叉的历史证据。`git log --oneline --graph --all` 单条命令展示所有方案分支、回溯路线和合并点。

#### 2. 回溯协议

任意管线阶段发现需回到之前阶段时，执行：

```
① 在当前分支记录触发信息（commit）
② git checkout -b backtrack/{当前阶段}-to-{目标阶段} {触发点的父commit}
③ 从目标阶段重新执行，逐阶段更新下游产物
④ 每完成一个下游阶段，检查受影响文件是否一致
⑤ 人类确认后合并回主线
```

下游一致性检查：回到阶段 N 后，对 N+1 及之后的每个阶段——该阶段的输入是否改变？无变化则跳过；有变化则重跑。

同一问题不允许重复回溯——第二次说明前提本身有根本缺陷，需人类裁定。

#### 3. Commit message 规范 — 信息密度是核心

git 历史的质量取决于 commit message 的信息密度。规范不是格式要求，而是**内容必须让未来的 AI 仅凭 message + diff 完全理解发生了什么**：

| 场景 | message 必须包含 |
|------|------|
| 阶段完成 | 阶段号 + 做了什么决策、产出了什么 |
| 方案变更 | 从什么变到什么 + 原因 + 数据证据摘要 |
| 批判修正 | 批判编号 + 改了什么 + 受影响的文件列表 |
| 数据修正 | 哪列/哪个样本 + 修正原因 + 前后对比 |
| 回溯 | `[回溯] {触发阶段}→{目标阶段}` + 原因 |

示例：

```
[批判7] 修正 [32,36) 组推荐时点 11→12 周

原因：Wilson CI 下界 49%，p₀=0.7 时达标率 40%，11周不可靠
影响：sub2-report.tex §3.2, comprehensive.tex 表3, final-paper.tex 表2
验证：Wilson CI 下界升至 71%，p₀ 灵敏度分析通过
```

关键：message 中**必须列出影响的文件**——这是 AI 做级联检查的依据。`git log --grep="{文件名}"` 可立即查询某文件的所有变动历史。

#### 4. 阶段级提交节点

阶段切换时自动提交，确保每个阶段有干净提交点供后续回溯切出：

- 0.2 — 数据清洗完成
- 1.1 — 方案决策树定稿
- 1.3 — 方案确认书签署
- 2.0 — 数学推导定稿
- 2.3 — 子问题报告初稿
- 3.0 — 批判审查前（切 review 分支点）
- 3.1 — 报告修正完成
- 4.0 — 终稿编译
- 4.1 — 终稿组装完成

#### 5. 命名规范

- **禁止** `final`、`final2`、`really-final` 等后缀
- 终稿放入 `final-paper/` 目录，目录名即表明身份
- 图表：`{子问题}-{内容}-v{N}.{格式}`，版本号递增，不覆盖旧版
- 同一文件的多次迭代：旧版移至 `archive/` 子目录

#### 6. 临时文件归档（P2）

终稿定稿后一次性执行：
- `outputs/scratch/` 下 `_` 前缀临时脚本 → `outputs/scratch-archive/`
- 被报告引用的实验脚本保留原位
- `scratch-archive/README.md` 标注各脚本用途

#### 实施优先级

| 优先级 | 措施 | 理由 |
|:---:|------|------|
| P0 | 分支策略 + commit 规范 | git 替代日志后，这是唯一需要做对的环节 |
| P0 | 阶段级提交节点 | 分支和回溯的锚点 |
| P1 | 回溯协议 | 解决 A+E 类问题的操作化方案 |
| P1 | 命名规范 | 规则简单 |
| P2 | 临时文件归档 | 终稿后一次性操作 |


## 五、人类使用反馈：管线深层问题

> 以下为人类在本轮全流程中的使用体验总结，记录了管线规则与实际执行之间的系统性偏差。

### 分类总览

按问题性质归为六类：

| 类别 | 编号 | 核心问题 | 解决层面 |
|------|------|------|------|
| **A. 方案变更与追溯** | 5.1, 5.2 | 方案偏离无记录，数学推导未同步 | 管线阶段规则缺失 |
| **B. 数据与领域知识** | 5.3, 5.6, 5.12, 5.19 | 预处理缺领域判断、问题目标理解不深、不查文献不研读、只用缓存不索引原始数据 | 新增阶段 0.0 + 深度问题重述 + 数据注释 |
| **C. 论证与探索策略** | 5.4, 5.10, 5.11 | 不跑基线 → 路径锁定 → 防御性论证（覆盖决策前中后） | 阶段规则 + 行为约束 |
| **D. 版本与流程管理** | 5.5, 5.16, 5.18 | 无分支、无 git、命名混乱、操作不可追溯 | 基础设施（流程规范） |
| **E. 批判处理机制** | 5.7, 5.8 | 无优先级排序、不检查级联效应 | 批判阶段执行逻辑缺陷 |
| **F. 报告与制品质量** | 5.9, 5.13, 5.14, 5.15, 5.17 | 方法透明性、图表分类/引用、流程图、分辨率 | 输出质量门禁 |
| **G. 代码质量与工程规范** | 5.20, 5.21, 5.22 | 公共代码重复、绝对路径硬编码、缺乏代码审查 | 代码规范 + 审查阶段 |

### 5.1 【A】方案变更无正式记录机制

**问题**：从确认书方案（马氏距离 + Z值）到实施报告（Fisher LDA + GC/QC 特征）的变更，散落在 .tex 报告的一句话中，无阶段性记录。子问题1 的 WLS、非线性、树模型三大探索方向的实验结果同样没有汇聚成决策依据文档——代码在 scratch/ 但论证过程丢失。

**后果**：(1) 批判审查时审稿人只能看到"方案被静默替换"的表象，无法追溯变更的合理性和数据依据；(2) 被 pass 掉的策略在后续审查中可能被重新提起，如果记录丢失就需要重跑实验。

**建议**：
- 方案变更通过 git 分支记录：切出 `experiment/{方案名}` 分支，commit message 携带偏离原因、数据证据、影响文件——分支即变更记录，不需文档内标记
- 被淘汰策略的实验结论保留在分支的 commit 历史中，`git log --graph` 可随时回溯，无需额外维护附录
- 方案变更时需检查新方案是否建立在旧方案错误的前提上——例如如果旧方案的前提（Z 值有信号）已被证伪，新方案不应继承任何依赖此前提的假设
- 方案定型后合并回主线，确认书中只留一句话指向相关 branch 即可

### 5.2 【A】方案变更后数学推导未同步更新

**问题**：管线将数学推导定稿在 `model-notes/math-*.tex`（阶段 2.0），但后续方案变更时不会回溯更新数学推导。这导致数学推导始终反映确认书方案，而非实际实施的方案。

**潜在风险**：极端情况下，模型可能用确认书方案的代码产出的数值结果，当作新方案的结果写入报告——因为 AI 不会自动区分"推导对应的代码"和"当前正在运行的代码"。

**建议**：回溯协议已覆盖此场景——方案变更触发回溯到阶段 2.0 时，应重新执行数学推导的完整工作，而非仅复用旧公式。关键在于回溯的实际含义是"重做该阶段的完整工作"，不是"把旧结果用在新数据上跑一遍"。

### 5.3 【B】数据预处理缺乏领域判断

**问题（子问题3 IVF 案例）**：辅助生育个体（8 例 IVF、9 例 IUI）应在数据清洗阶段（0.2）就排除——因为非自然受孕的孕妇处于生殖中心全程增强监护下，不适用普查式 NIPT 时点推荐。但管线将这类决策推迟到建模阶段，导致辅助生育编码（0/1/2）被当作连续变量纳入回归，产生 p=0.075 的虚假信号，直至批判阶段（批判8）才被发现和修正。

**根因分析**（三个层面）：
1. **领域知识缺失**：不知道 IVF/IUI 人群临床管理路径不同，应在清洗阶段排除
2. **问题目标理解不深**：做完问题重述就放下，未追问"普查式 NIPT 时点推荐"结论天然排除生殖中心增强监护人群
3. **数据认知遗忘**：G 列 IVF 三种标签（0/1/2）需要编码，回头看数据时忽略此列，AI 在回顾数据时会丢失之前对数据构成的认知

**建议**：
- 每个子问题启动时新增**深度问题重述**环节（阶段 1.0）：对赛题数据、子问题目标、实际情况做一次深化分析，明确——适用边界（结论被谁、在什么场景下使用？哪些人群明确不适用？）、数据桥接（哪些变量直接回答此问题？哪些表面相关实则不应使用？）、实际约束（该问题的临床/工程常识是什么？），输出后需人类确认
- 阶段 0.2 清洗完成后建立**数据列注释**（存入 `domain-knowledge.md` 数据区）：每列记录原始编码含义、是否排除及理由、转换映射、已知异常模式；后续阶段加载数据时强制回顾注释，避免遗忘关键变量
- 阶段 0.2 增加"领域排除检查"——结合 domain-knowledge.md 和深度问题重述，识别因临床路径不同而应整体排除的子群体，排除决策在清洗阶段完成而非推迟到建模

### 5.4 【C】策略论证倾向防御性而非主动证明

**问题**：AI 在面对批判时倾向于"证明现有策略没错"，而非"主动证明此策略比替代策略更优"。例如：
- 批判 6（40+ 组 n=1）的处置：通过回溯 8 人数据验证了两阶段策略的安全性 → 这是"策略没错"
- 但未主动追问：如果不用两阶段而用单一保守时点（如 20 周所有人都检），效果如何？→ 这是"策略比替代策略更优"

**建议**：在阶段 3.1（报告修正）中，对每条批判追加一个"主动验证"环节——不仅回应批判，还要证明当前方案在可选的替代方案中是最优的。

### 5.5 【D】批判审查应使用分支机制

**问题**：批判审查（阶段 3.0）直接在主线上修改报告，如果审查结论后续被推翻或需要回退，没有干净的版本点可恢复。

**建议**：阶段 3.0 启动时提醒人类创建 git 分支，所有批判修正在分支上进行，人类确认后合并回主线。

### 5.6 【B】缺乏赛题领域知识查询步骤

**问题**：模型对 NIPT 领域的基础临床知识完全依赖赛题提供的信息，不会主动查询技术文献。例如：临床文献中 NIPT 对 T21 检出率 > 99%、T18 > 97%、T13 > 80%——这些数据在子问题4 的 Z > 3 召回率仅 4.48% 时本应作为关键的"异常信号"被识别，但因为不知道临床基准而仅被当作"数据特征"。

**建议**：管线新增阶段 0.0（领域知识整理），在问题拆解后、数据清洗前完成。检索分两类，全部汇入 `solution/domain-knowledge.md`：
- **非文献类**：临床基准值（如 T21 检出率 >99%）、标准实践（NIPT 推荐孕周窗口）、关键数值——通过 WebSearch 或临床指南获取
- **文献类**：检索到的论文逐篇研读，提取核心结论、方法、适用条件，以结构化条目录入（附带完整引用信息：作者/年份/标题/DOI/链接），原文 PDF 存档至 `solution/references/`

`domain-knowledge.md` 作为项目级知识基座，包含非文献知识、文献摘要、数据注释三个分区，所有后续阶段可单文件检索全部已知信息。文献区同时解决 5.19（引用研读留存）——后续所有引用从此调取，不再仅凭模型记忆凭空生成。后续任何阶段检索到的新文献，同样走研读→录入→存档流程，追加到此文件。

### 5.7 【E】批判处理缺乏优先级排序

**问题**：阶段 3.1 中 14 条批判 + 4 条共性问题按编号顺序逐条处理，而非按影响范围排序。如果编号靠后的大前提问题（如批判 10：方案本身被替换）先被发现，可能会推翻前面已完成的修正（如批判 1-9 的措辞调整）。

**建议**：阶段 3.0 批判阅读阶段保持自由批判——审稿人不排序、不自我审查，看到什么说什么。批判阅读完成后、进入 3.1 回应之前，新增一个**排序环节（阶段 3.0→3.1 过渡）**，人类 + AI 共同对批判清单按影响范围分层排序：

| 层级 | 影响范围 | 典型问题 | 处理规则 |
|------|------|------|------|
| **前提层** | 推翻后所有下游结论失效 | 方案本身被替换、数据排除标准有误、问题目标理解偏差 | 排在最前；处理时先停下等人类裁定是否继续 |
| **方法/参数层** | 影响某子问题的结论，但前提不变 | 模型参数调整、阈值重设、分组方式变更 | 前提层清完后处理 |
| **表达层** | 仅影响措辞、图表标注，结论不变 | 用词过于绝对、图表缺少标注、格式问题 | 最后处理 |

同层内按子问题分组，便于级联追踪。排序后在清单中标注层级和子问题标签，例如 `[前提层/子问题4] 方案变更透明度`、`[表达层/子问题2] Wilson CI 标注完整`。

**排序标准不是"严重度"，而是"影响范围"**——越底层的问题越靠前，因为底层一改，上层全部需要重做。

### 5.8 【E】批判修正的级联效应缺乏考量

**问题**：批判修正可能产生数据或结论的级联变化，但管线未要求 AI 在处理每条批判后检查对其他部分的影响。例如：批判 7 将 [32,36) 组时点从 11 周改为 12 周——这会影响子问题3 的分组一致性验证和终稿的所有相关表格。

**建议**：级联检查分两层执行：

1. **排序阶段预判**（3.0→3.1 过渡）：按 5.7 的分层排序后，对每个方法/参数层和表达层的批判标注可能受其影响的子问题和文件——因为同层按子问题分组，跨子问题的级联关系可在排序阶段一并识别。例如批判 7（方法层/子问题2）直接影响子问题3 分组一致性验证和终稿表格。
2. **处理后的逐条确认**（3.1 执行中）：每条批判修正完成后，对照预判的级联清单逐项检查受影响的文件/段落/表格是否需要同步修改。级联清单在处理过程中动态更新——如果前提层某条导致方法层某条失效，标记跳过而非强行修改。

### 5.9 【F】方法透明性不足

**问题**：代码中已实现的技术细节在报告中被省略。典型案例：Fisher LDA 实际使用了 Tikhonov 正则化（`reg=0.01×trace/n`）解决小样本下协方差矩阵奇异问题，但报告初稿完全未提及正则化——审稿人只能从理论层面推断"协方差估计应该不成立"（批判 14）。

**建议**：阶段 2.3（报告初稿）增加"代码-报告技术细节交叉检查"——凡是代码中做了但报告未提的关键技术决策（正则化参数、收敛判据、带宽选择等），必须补充至报告方法部分。

### 5.10 AI 不先跑简单基线

**问题**：方案探索时 AI 倾向于直接生成完整方案（如 Fisher LDA + 多特征融合），而不先跑简单规则（如单特征阈值、OR 规则）。虽然成熟方案大多数时候有效，但这可能导致过度设计——批判 14 的方案对比实验（单特征 vs 等权组合 vs Fisher LDA）实际上是事后补的，并非探索阶段的自然步骤。

**建议**：阶段 1.1（方案决策树）A 类验证实验中，强制加入"简单基线"步骤——在生成任何成熟方案前，先用最简单规则（单特征阈值、OR/AND 组合、线性回归）建立性能下界。

### 5.11 【C】路径锁定——一旦选定路线，后续忽略替代

**问题**：AI 在决策树阶段选定一条技术路线后（如联合建模），后续所有阶段都会忽略另一条路线（如模块化组合）。即使批判阶段暴露了当前路线的问题，AI 也只会在已选框架内修补（加特征、调参数），不会重新打开"融合 vs 模块化"的对比。本质上是一种路径依赖——早期决策锁死了后续探索空间。

**建议**：在关键决策点（阶段 1.1 决策树、阶段 3.1 批判修正）设置"重新打开对比"的触发条件——当批判触及方案架构层面时，强制重新评估被放弃的替代路线。

### 5.12 【B】过度依赖处理后的数据

**问题**：AI 始终从 `outputs/data/` 的 pickle 缓存加载数据，不去查看原始 Excel。这导致：(1) 数据清洗中的错误被固化在缓存中，后续不可见；(2) 原始数据中的异常模式（如数据录入错误、不成比例的空值分布）被预处理掩盖。

**建议**：
- 阶段 0.2 清洗完成后，在数据列注释中记录每列的原始来源索引——原始列名、预处理丢弃了哪些值（多少条、为什么）、是否存在被处理掉但可能相关的信息。后续阶段看注释即知原始数据中有哪些内容，无需每次回头翻 Excel
- 批判审查阶段（3.0），要求至少一次用原始 Excel 验证关键结论

### 5.13 【F】Artifact 分类缺乏阶段性确认

**问题**：所有图表统一放在 `artifacts/charts/` 下，不区分"正文用""附录""不放入"。直到终稿编译时才一次性分类，此时图表数量庞大（30+ 张），极易混乱。

**建议**：图表分类在三个时间点执行：
- 每个子问题阶段 2.2（结果分析）：对当前子问题的图表做初步三类分法
- 批判审查每次修改后：重新确认受影响图表的分类
- 阶段 4.0（终稿时）：最终汇总确认

### 5.14 【F】报告中图表引用遗漏

**问题**：AI 在子问题报告中频繁忘记引用已嵌入的图表，导致 PDF 中出现"图??""表??"

**建议**：
- 阶段 2.3 编译前：强制检查每个 `\begin{figure}` 和 `\begin{table}` 是否有对应 `\label{}`——这是根因，`??` 只是症状
- 阶段 2.3 编译通过后：自动扫描 PDF 中是否出现 `??`，如有则强制修正（兜底）

### 5.15 【F】流程图绘制薄弱

**问题**：TikZ 绘制流程图质量较低，但 matplotlib 在此场景下表现同样不佳——两种工具都难以产出排版级别的流程图。具体选型需要实际测试对比（如 draw.io、Python graphviz、Mermaid + 渲染等），在赛前确定最优工具链。

### 5.16 【D】版本管理缺失

**问题汇总**：
- AI 不做 git 管理，修改即丢失历史
- 命名惯用 `final`，导致多次修改后文件名与实际状态脱节
- review-notes 中每条"终稿操作"无执行记录——换个窗口就可能重复操作或遗漏
- scratch/ 下大量 `_` 前缀临时脚本未清理归档

**建议**：
- 每个阶段结束时 AI 自动执行 `git add -A && git commit`，commit message 携带完整的决策依据和影响文件清单
- 禁止使用 `final` 作为文件名后缀，改用日期时间戳
- 以 git 为唯一真相源——批判操作、方案变更、回溯全部通过 commit + 分支记录，不额外维护日志文件
- 终稿定稿后将 scratch/ 下临时脚本归档到 `outputs/scratch-archive/`

### 5.17 【F】图表分辨率偏低

**问题**：AI 默认 dpi=150，在大尺寸图中细节模糊。

**建议**：所有论文用图 dpi 不低于 300，散点图附加透明度处理避免重叠。

### 5.18 【D】终稿组装无操作记录

**问题**：终稿组装过程中从内部报告提取内容、重组章节、增减图表的每一步都没有记录，后续如果需要回溯某段文字的来源或某张图为什么被删，完全不可追踪。

**建议**：阶段 4.1 组装过程在独立分支 `assemble/final` 上进行，每个章节的增删改作为独立 commit，commit message 标注来源和取舍理由。`git log` 即组装记录。

### 5.19 【B】引用文献无研读、无留存规范

**问题**：AI 在报告中引用文献时不会预先研读原文——仅凭模型内部知识生成引用内容，不验证原文是否确实支持引用的论点。此外没有统一的文献留存规范——三篇引用中两篇未提供链接或 DOI，后续核查困难。

**后果**：(1) 引用可能被误用或张冠李戴——例如 postmortem 三(5) 中发现的 GC 含量文献问题（Mouliere et al. 研究的是片段长度分布而非染色体特异性 GC 含量）；(2) 审稿人或人类无法追溯引用来源验证其准确性。

**建议**：并入 5.6 的文献检索流程。所有检索到的论文走统一管线：研读原文 → 提取核心结论/方法/适用条件 → 以结构化条目汇入 `domain-knowledge.md` 文献区（附带完整引用信息：作者/年份/标题/DOI/链接）→ 原文 PDF 存档至 `solution/references/`。阶段 2.3 报告初稿引用时从 `domain-knowledge.md` 调取，禁止仅凭模型记忆生成引用。每条引用在 `.bib` 中必须填写 url/doi 字段。

### 5.20 【G】公共代码重复定义

**问题**：代码审查发现两处大规模重复：

- `pgw()` 孕周解析函数在 `sub1-*.py`、`sub2-model.py`、`_check_*.py` 等 9 个文件中各自复制了一份完全相同实现。同时 `sub2-model.py` 和 `_wilson_pass_rate.py` 跳过了 `pgw()` 直接用 `孕周_数值`，取数逻辑不一致。
- 月份哑变量构建 + 技术变量 z-score + gw_c/bmi_c 中心化的特征工程代码块在 sub1 相关文件中复制了 7 次。

**后果**：(1) 函数修改时需同步 9 个文件，极易遗漏；(2) 同一列的数据可能因取数路径不同而产生静默不一致。

**建议**：阶段 1.2（代码框架搭建）增加规则——同一逻辑重复 ≥3 次即提取为公共模块（`utils.py`），所有脚本统一 import。公共模块的变更通过 git diff 一目了然，不影响各子问题的独立脚本。

### 5.21 【G】绝对路径硬编码

**问题**：所有 Python 文件硬编码了 `E:\MathModel\...` 绝对路径，代码无法在其他机器上运行，也无法被他人复现。

**建议**：代码规范增加可移植性规则——所有路径用 `pathlib.Path(__file__).parent.parent` 相对定位项目根目录，禁止硬编码盘符和绝对路径。

### 5.22 【G】缺乏代码审查环节

**问题**：代码审查在 `sub4-model.py` 中发现两处 bug（`date_map.set_index().loc[]` 可能 KeyError、协方差归一化公式不符合 Tikhonov 正则化标准），以及 `sub4_contrast_analysis.py` 与 `sub4-model.py` 的去重逻辑不一致。这些问题是方案确认书签署后、正式跑数据前本应被发现的。

**根因**：管线在确认书（阶段 1.3）之后直接进入实验（阶段 2.0），中间没有代码质量门禁。确认书只锁定了方案设计，没有锁定实现是否正确。

**建议**：新增阶段 1.5（方案代码审查），在确认书签署后、正式跑数据前执行：

- 检查代码逻辑是否与确认书方案一致
- 检查关键公式实现是否正确（对照确认书的数学推导）
- 检查不同子问题的共享数据处理逻辑是否一致（如同一样本的筛选条件、去重方式）
- 检查关键注释与实际代码是否匹配（避免"打印'线性混合效应'但实际用 OLS"这类问题）

代码审查由 AI 自动执行，不作为本管线的人类确认关卡——代码量过大，人类无法逐行审查。管线需配备专用的代码审查 skill（如 TRAE-code-review），审查结果以清单形式输出，只向人类汇报关键问题和审查结论，细节由 AI 自行处理。


## 六、论文质量专项（AI 评审反馈）

> 以下为让 AI 以审稿人身份对论文提出的改进点。

### 6.1 模型假设验证薄弱

| 假设 | 当前状态 | 缺失 |
|------|------|------|
| 条件对数正态性 | 仅报告偏度从 0.70 降至 −0.55 | 未提供 Shapiro-Wilk 正式检验 |
| Fisher LDA 线性可分性 | AUC=0.775 仅表明"中等可分" | 未对比非线性方法（核 LDA、SVM）|

**分析**：

- **Shapiro-Wilk 缺失**：是管线问题，不是知识库问题。子问题1 实际做了 Shapiro-Wilk（见知识卡片评估表），AI 知道这个方法。但子问题4 的 Fisher LDA 线性可分性假设就没有做类似验证——说明管线没有把"假设检验"作为每个子问题的强制步骤。**建议**：阶段 2.0（数学推导）增加要求——每个子问题必须列出模型的核心假设，并对每条假设给出检验方法和结果，不因模型不同而跳过。

- **非线性对比缺失**：实际上子问题1 探索过 WLS、立方项、随机森林，子问题4 对比过单特征阈值、等权组合、Fisher LDA——探索的方法比此处列出的还多，但结果未写入报告。根因与 5.1（方案变更无记录）相同——探索了但论证过程丢失。git 分支策略（D 类）已覆盖"记录"层面，5.9 代码-报告交叉检查已覆盖"写入"层面，但应再加强一条：**被淘汰的方案必须在报告局限部分或附录中简要交代"尝试了 X/Y/Z，因原因 A/B/C 而选择当前方案"**——这既是诚实的科学实践，也比"仅对比一个方法"更有说服力。

### 6.2 子问题4 过拟合风险未充分诚实

- 147 人中仅 16 例异常，无法划分训练/测试集
- 虽已使用 Tikhonov 正则化，但无独立验证集，93.8% 召回率可能是乐观估计
- **建议**：至少报告 LOOCV 结果

**分析**：子问题4 只有 16 个异常样本，没法像常规做法那样切训练集/测试集来评估泛化能力。93.8% 的召回率是在全量数据上算的——模型见过这 16 个人，再去判断这 16 个人，成绩自然会偏高。这就像让学生考一遍做过的卷子，分数说明不了真实水平。

管线应该做的事：当建模阶段发现"样本太少、无法独立验证"时，强制要求替代方案——比如 LOOCV（每次留一个人做测试，其余 146 人训练，轮 147 次取平均）。这比事后审稿人追问再做要好得多。

推广来看，子问题1 的中介分析也有同样性质的问题——算了中介比例但没做 Bootstrap 置信区间。这两件事的本质是同一个坑：**管线没有要求每个核心结论必须配上不确定性量化**（置信区间、交叉验证、Bootstrap 区间等），导致报告中出现"孤零零的数字"——看起来精确，其实读者不知道这个数字有多可靠。建议将此作为建模阶段的强制规则。

### 6.3 技术细节缺失

| 缺失项 | 位置 | 根因 | 覆盖 |
|------|------|------|:---:|
| Loess GC 校正的 span 带宽参数 | 子问题4 | 代码有、报告没写 | 5.9 代码-报告交叉检查 |
| Fisher LDA 特征选择过程 | 子问题4 | 探索过、记录丢失 | 6.1 被淘汰方案写入报告 |
| 中介分析 Bootstrap 置信区间 | 子问题1 | **没做**——配了方法但没配验证手段 | 6.2 不确定性量化规则 |

### 6.4 临床可操作性讨论不足

- 未讨论孕周估算误差（±1 周）对达标率的实际影响
- BMI ≥ 40 组两阶段策略未估算经济成本（单次 NIPT 约 1000–3000 元）

**分析**：两个缺失项指向同一个深层问题——管线做了 p₀ 灵敏度分析后，认为"稳健性检查已完成"，但灵敏度分析并非单一固定流程。p₀ 检查的是**参数假设维度**（阈值变了结论变不变），而孕周误差是**输入测量维度**（输入本身有误差时结论变不变），经济成本是**输出落地方案**（建议被执行时实际代价多大）。三个维度互不替代。

关键不是"灵敏度分析做少了"，而是管线没有在结果产出后强制问一句：**这个结论在真实世界里可能被什么翻掉？** 翻不掉就过，翻得掉就补分析。本质上与 5.3 深度问题重述（前置）和 5.4 主动证明（决策）的思维一致，只是位置不同——这里是后置的结果落地检查。

**建议**：阶段 2.2（结果分析）新增**实际落地检查**，两条必答题：

1. **输入鲁棒性**：模型的核心输入变量在现实中有多大测量误差？结论对这份误差敏感吗？需要做输入维度灵敏度分析。（对应孕周 ±1 周）
2. **输出成本**：模型建议如果被执行，带来什么实际成本或风险？是否需要量化讨论？（对应经济成本）

阶段 1.0（深度问题重述）配合增加提示——列出关键变量的真实世界属性（精度、可靠性、覆盖范围），为 2.2 的落地检查提供检查清单。

### 6.5 图表质量问题

- 残差 vs 拟合值散点图 1082 个点严重重叠，需透明度或六边形分箱
- ROC 曲线未标注阈值点

**分析**：两处问题的本质相同——AI 把图表生成当成技术任务（"你要求散点图→我画散点图"）而非沟通任务（"这张图在论文里要传达什么信息，读者需要看到什么"）。散点图 1082 个点用默认不透明度糊成一团，ROC 缺 Youden 点标注——都是因为 AI 没有针对场景做形式适配。

纯管线规则只能做事后检查（"画完了？自查一下"），治标不治本。需要两层配合：

- **skill 层**：配备图表生成专用 skill（如 chart-generator），将论文图表质量标准焊入生成环节——数据量感知散点形式（大样本自动加透明度或六边形分箱）、ROC 必定标注决策点、默认 dpi ≥ 300 等。AI 一键调用，降低遗漏概率。
- **管线层**：阶段 2.2 产出图表后增加**图表自查规则**——每张图回答两个问题：① 以当前数据量和分布，图的形式选对了吗？② 读者需要从这张图获取什么信息，标出来了吗？作为 skill 层的兜底检查。

### 6.6 内部报告有但终稿遗漏的内容

| 内容 | 来源 | 重要性 |
|------|------|:---:|
| ~15% 孕妇首次达标超 16 周——"补测不损失信息"的关键事实 | Sub2 | 高 |
| 40+ 组个体内 CV 均值 39.4% vs 其他组 17–25%——量化个体波动 | Sub2 | 高 |
| 41 条 Z 值异常但无标注样本分析（37 条被标记为有风险） | Sub4 | 中 |
| 三分类输出表（有风险/不确定/低风险人数） | Sub4 | 中 |
| 80% 等早期达标值的数据依据 | Sub2 | 低 |

**分析**：遗漏的根因是 20 页硬约束导致压缩阶段被动删减——这些内容并非被主动判定为"不重要"，而是压缩过程中被挤掉，且删除时无记录。实际优秀论文正文篇幅可达 26–36 页，20 页不应作为硬约束。

**建议**：
- 取消 20 页硬约束，正文篇幅由内容质量而非页数决定
- 每个子问题内部报告完成后标记 3–5 条"不可丢失的关键发现"；终稿组装时逐条确认去留地位（正文/附录/舍去并记录理由），确保所有删除是有意识的决策而非遗漏

## 七、AI 使用边界与合规策略

### 7.1 问题定位

本次建模采用人机协同探索模式——AI 参与了方案生成、批判辩论、结果分析和报告撰写。这与竞赛规则中"核心建模与分析必须由参赛队独立完成"的要求存在张力。需要将"AI 主导探索"呈现为"人类指挥、AI 执行"。

### 7.2 合规策略

1. **代码实现**：人类设计算法逻辑与数学模型，AI 辅助编写代码、排查 Bug、调参
2. **数据求解**：人类确定求解方法，AI 辅助进行数据清洗、数值计算或算法跑批
3. **排版编译**：AI 将人类撰写的文字、公式和图表转化为 LaTeX 代码并编译

### 7.3 提交策略

- 将最终报告中的技术性手段还原为提示词形式，体现人类在探索和批判性思考中的主导地位
- 在《AI 工具使用详情》中清晰展示人类构思算法思路、AI 辅助实现代码的过程
- 提供关键 Prompt 和人工修改代码的记录
- 明确声明：AI 仅用于代码辅助生成与 LaTeX 编译，模型假设、核心公式推导、算法设计思想及结果分析均由人工独立完成

### 7.4 正文标注规范

**7.4.1 标注在管线中的位置**

标注动作发生在终稿撰写阶段，但标注依据必须贯穿全管线持续积累——仅凭最后记忆标注必然遗漏和失真。每个阶段产出内容时，即时记录 AI 贡献点。

| 管线阶段 | 产出物 | 标注追踪需求 |
|---------|--------|-------------|
| 1.1 问题重述 | 深度重述文档 | AI 辅助分析的边界 |
| 1.2–1.3 方案设计 | 确认书 | 模型选择的 AI 建议来源 |
| 2.0 实验 | 代码、数据、图表 | 代码生成、图表生成来源 |
| 3.0 内部报告 | 子问题报告 | 分析文字、结论表述来源 |
| 4.0 终稿 | 正文 .tex | 汇总所有阶段标记，正式标注 |

**7.4.2 标注形式：正文 [AI-X-Y] 索引**

- **正文**：在 AI 参与的段落/公式/图表处插入索引标记 `[AI-X-Y]`（X=子问题 1–4，Y=序号），仅作索引，不附带说明文字。
- 全部描述（工具、用途、交互记录、采纳修改）放在 `AI工具使用详情.pdf` 中，`[AI-X-Y]` 即为指向该文件中对应条目的索引。
- **不设附录明细**——信息已在详情文件中，无需重复。

示例：

```
正文：采用 Fisher 线性判别分析结合 Tikhonov 正则化进行分类 [AI-4-1]。
详情 [AI-4-1]：所用工具 DeepSeek-R1-0528，使用目的为 Fisher LDA 方案验证……（详见 AI工具使用详情.pdf）
```

**7.4.3 AI 贡献参与等级分类**

按 AI 参与深度分五级，决定是否标注及标注措辞：

| 等级 | 场景 | 是否标注 | 标注措辞 |
|------|------|:---:|---------|
| I. AI 直接生成 | AI 输出分析文字，直接写入报告 | 必须 | "本段内容由 [工具] 生成，经人工审核" |
| II. AI 生成框架，人工填充 | AI 提供公式框架，人工调整参数 | 必须 | "由 [工具] 辅助生成，经人工修正" |
| III. AI 提供思路，人工独立撰写 | AI 建议模型方向，人理解后自行推导 | 建议 | "模型思路参考了 [工具] 的建议" |
| IV. 纯人工撰写 | 人写内容，AI 仅做格式/编译 | 不标 | — |
| V. AI 生成代码，论文描述算法 | AI 写代码，人根据代码写算法描述 | 建议 | "算法实现由 [工具] 辅助" |

**核心判断标准**：撤掉 AI 贡献后，该部分内容是否会实质性改变？若会→标注；若仅排版/语法等表面改动→不标。

**7.4.4 管线落地方案**

**第 1 步（贯穿全管线）**：每个阶段产出的 Markdown 报告中新增固定小节 `## AI贡献标记`，以表格即时记录：

```markdown
## AI贡献标记

| 序号 | 贡献内容 | 工具 | 等级 | 备注 |
|------|---------|------|:---:|------|
| 1 | 子问题4 模型方案建议 | DeepSeek-R1-0528 | III | 人工验证 Tikhnov 参数后采纳 |
| 2 | 子问题1 WLS 回归代码 | GitHub Copilot | V | 人工调参 |
```

**第 2 步（终稿阶段）**：汇总所有阶段的标记清单，在正文相应位置插入 `[AI-X-Y]` 索引，详情文件由 skill 自动编译。

### 7.5 AI 工具使用详情的编译规范

根据规定，"AI 工具使用详情"需包含：工具名称版本、使用目的和环节、关键交互记录、采纳和人工修改情况。本节建立统一的编译格式。

**7.5.1 核心原则：人类决策叙事**

不按"人机交互流程"记录，按"人类决策序列"记录。同样的工作，换一种叙事——

- 不是"AI 发现了什么" → 而是"人判断了什么、AI 协助验证了什么"
- 不是"AI 提出了方案" → 而是"人给出方向、AI 执行计算"

**7.5.2 单条目格式**

`AI工具使用详情.pdf` 中每个条目包含规定的四个部分。编号采用 `[AI-X-Y]`（X=子问题，Y=序号）。

```
[AI-X-Y]

所用AI工具名称和版本：
DeepSeek, DeepSeek-R1-0528, 深度求索（DeepSeek）

具体使用目的和环节：
[人做了什么决策、用到什么环节]

关键交互记录（重要提示词与回复）：
> 提示词：[体现人类给出方向、AI 执行的提示词，做绿色模拟]
  AI 回复：[关键结果摘要，可引用相关代码文件]

采纳和人工修改情况：
[人如何评估、修改、采纳]
```

注意：此格式仅用于 `AI工具使用详情.pdf`。论文参考文献区引用 AI 工具使用不同的简化格式（参见 7.5.5）。

**7.5.3 绿色模拟**

关键交互记录中的提示词不以原始对话贴入，而是做"绿色模拟"——将人类在 AI 之外完成的讨论和决策，融入提示词的表述中。AI 回复截取关键结果即可，相关代码以文件名引用（如 `sub4_fisher_lda.py`）。

示例见 [AI-4] 条目（子问题4 Fisher LDA 判别模型）。

**7.5.4 注意事项**

- 内部报告可由 AI 全程编译（中间产物，不提交，不受约束），终稿正文由人类撰写、AI 仅做 LaTeX 编译
- 知识库为赛前人类积累，不向赛方提供内容，但可转化为"赛前已确定 X 策略，比赛时要求 AI 执行 X"的人类决策陈述
- 提示词仅放关键决策轮次，不必全量贴入；同一工具的多次使用可按子问题合并为一个条目（日期写起止范围）

**7.5.5 论文参考文献区格式**

与 `AI工具使用详情.pdf` 不同，论文参考文献区按工具（非使用场景）分行，同一工具只列一次。格式遵循规定第4条第(1)款：

```
[编号] 工具名称，版本/型号，开发机构/公司，使用日期。
```

示例：`[1] DeepSeek, DeepSeek-R1-0528, 深度求索（DeepSeek）, 2025-09-05 到 2025-09-07.`

如果使用了多个工具，每个工具一行，编号按在论文中首次出现的顺序排列。

### 7.6 管线与 AI 工具使用详情编译器的接口

本节定义管线各阶段如何向 `ai-usage-report` skill 提供数据，以及 skill 如何回传结果。

#### 7.6.1 调用时机

```
管线阶段      1.x    2.0    3.0    4.0    提交前
              │      │      │      │      │
AI贡献标记 ── 每阶段产出的内部报告均附带 ## AI贡献标记 表格
              │      │      │      │      │
skill调用 ───────────────────────────────→ 终稿编译完成后调用
                                            生成 AI工具使用详情.pdf
```

skill 在阶段 4.0（终稿编译）完成后、提交支撑材料前调用。此时所有子问题的内部报告已定稿，AI 贡献标记表完整，绿色模拟所需的人类决策上下文也已齐备。

#### 7.6.2 输入契约：`## AI贡献标记` 表格式

各阶段内部报告的 `## AI贡献标记` 节必须包含以下字段的表格：

```markdown
## AI贡献标记

| 序号 | 子问题 | 贡献内容 | 工具 | 版本 | 等级 | 日期 | 相关代码 |
|------|:------:|---------|------|------|:---:|------|---------|
| 1 | 1 | 混合效应模型方案讨论 | DeepSeek | R1-0528 | III | 09-05 | sub1_mixed_model.py |
| 2 | 4 | Fisher LDA 方案验证与实现 | DeepSeek | R1-0528 | V | 09-06 | sub4_fisher_lda.py |
```

**字段说明**：

| 字段 | 必需 | 说明 |
|------|:---:|------|
| 序号 | 是 | 该阶段内的递增编号，用于追踪 |
| 子问题 | 是 | 1–4，标记属于哪个子问题 |
| 贡献内容 | 是 | 一句话概括 AI 帮了什么 |
| 工具 | 是 | 工具名称 |
| 版本 | 是 | 工具版本/型号 |
| 等级 | 是 | I–V，参考 7.4.3 参与等级分类 |
| 日期 | 是 | 使用日期（单日或起止） |
| 相关代码 | 否 | 生成代码的文件名，多个用逗号分隔 |

#### 7.6.3 Skill 输出回传

skill 生成两个产物，对接终稿：

| 产物 | 位置 | 用途 |
|------|------|------|
| `AI工具使用详情.pdf` | 支撑材料目录 | 提交给赛方（按 [AI-X-Y] 条目组织） |
| `ai-references.tex` | 终稿目录 | 论文参考文献区的 AI 工具引用，终稿 `\input` 引入 |

`ai-references.tex` 格式（按工具分行，同一工具只列一次）：

```latex
% 由 ai-usage-report skill 自动生成，请勿手动编辑
[1] DeepSeek, DeepSeek-R1-0528, 深度求索（DeepSeek）, 2025-09-05 到 2025-09-07.\\
[2] GitHub Copilot, GPT-4o, GitHub, 2025-09-05 到 2025-09-07.\\
```

终稿 `.tex` 中引用方式：

```latex
\section*{参考文献}
... 普通参考文献 ...

% AI工具
\subsection*{AI工具}
\input{ai-references.tex}
```

#### 7.6.4 编号一致性

存在两套独立的编号体系：

| 编号体系 | 格式 | 出现位置 | 含义 |
|---------|------|---------|------|
| 详情条目编号 | `[AI-X-Y]` | 正文索引 + AI工具使用详情.pdf | X=子问题，Y=该子问题内序号 |
| 参考文献编号 | `[1]`, `[2]`… | 论文参考文献区 | 每个工具一个编号 |

两种编号不互相引用，各自独立。人类在正文中插入 `[AI-X-Y]` 标记后，应与 skill 生成的 `AI工具使用详情.pdf` 中的条目编号交叉核对，确保一致。

#### 7.6.5 绿色模拟环节

标记表是**原始事实记录**（做了什么），skill 在编译时执行绿色模拟（怎么表述）。标记表不要求叙事转化——如实记录即可：

```
原始记录（标记表）: Fisher LDA 方案验证与实现
绿色模拟（skill输出）: 团队锁定 Fisher LDA 降维方向后，要求 AI
                     实现 Tikhonov 正则化并进行性能评估
```

转化由 skill 自动完成，人类在 skill 输出后审核表述是否准确。


## 八、终稿组装策略反思

### 当前做法
"先改小论文 → 合并大论文 → 压缩至要求页数"的三阶段方案。

### 问题
实际操作中该方案并不好用——修改小论文后合并时产生大量格式冲突和内容重复；压缩阶段需要大量删减导致逻辑断裂和重要内容丢失。

### 改进方案

1. **取消 20 页硬约束**：优秀论文正文可达 26–36 页，篇幅由内容质量决定，不作强制压缩。同时取消三阶段中的"压缩"环节。
2. **正文与附录并行编译**：正文 `.tex` 和附录 `.tex` 各自独立编译，最后合并 PDF。避免格式冲突，修改时各自迭代互不干扰。
3. **直接编辑终稿**：内部报告只作为素材库，不做"中间形态的论文"。从内部报告按需提取内容到终稿 `.tex`，始终在同一个文件上迭代，消除合并环节。
